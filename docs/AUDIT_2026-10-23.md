## Findings

### F1 — HIGH (operational): the GitHub repository is public, and the legacy database remains in its history

Verified via the GitHub API on 2026-10-23: `iwani1/claude-test` is
`public`. The 2026-10-19 audit recorded that the legacy RestPOS database
was removed from the tip but **retained in git history**, with closure
conditional on the repo being private and the history purged. It was
later made public so the VPS could pull over HTTPS, and it is still
public now. Anyone can clone the full history and recover that database
(legacy credentials and historical business data). This sandbox holds a
shallow checkout, so the exact blobs could not be re-enumerated from
here; until someone verifies otherwise on a full clone, the database
must be treated as exposed. The rotated `pos_owner` password limits —
but does not eliminate — the impact: the historical data itself is the
exposure. No application code change can close this; it is a
repository-settings and history question (the owner previously ruled out
storing databases on GitHub going forward).

### F2 — LOW (audit trail): quick PIN-switch rows still name the outgoing user

`src/app/api/auth/switch-pin/route.ts` writes the audit row with
`userId`/`userName` of the person switching **away**, and the incoming
user only as a numeric `entityId`. Anyone reading Audit Logs sees
"X switched" where X is who left, not who arrived. This exact ambiguity
already complicated one real investigation (the disputed GH₵420
payment, Oct 2026). Data is not wrong at the storage level for orders
(`orders.userId` vs `payments.processedBy`), but this row type misleads
a reader.

### F3 — LOW (accessibility): hold-to-confirm has no alternative activation

Permanent deletions (orders, staff, and the hold variant of
`ConfirmDialog`) require a sustained 1.4 s press. Keyboard hold
(Space/Enter) works and `prefers-reduced-motion` is honoured, but a
user who cannot sustain a press has no equivalent single-activation
path. Cancel is unaffected. This is a deliberate friction trade-off,
recorded here so it stays a conscious one.

### F4 — INFORMATIONAL: deleted-dish list is readable by any signed-in session

`GET /api/menu?includeArchived=1` is gated only by having a session.
The Menu Manager hides Deleted items from non-owners and the API
refuses non-owner delete/restore, but any staff login can still fetch
archived dish names/prices directly. Cost prices remain hidden from
cashiers as before. Sensitivity is low (it is the same data the menu
itself shows), noted for completeness.

### F5 — INFORMATIONAL: dependency advisories are dev-only

`npm audit`: 4 moderate advisories, all in the `drizzle-kit`/`esbuild`
development toolchain. The production dependency tree is 7 packages and
reports **0 vulnerabilities** (`--omit=dev`, the CI gate). Per standing
policy no `npm audit fix --force` was run.

### F6 — INFORMATIONAL: dish-photo data URLs grow the menu payload

Photos uploaded through the new Menu Manager dropzone are stored as
data URLs on the item and returned by `GET /api/menu` to every session.
A handful of photos is negligible; at 165 dishes with photos the
payload (and till load time) grows by the total photo weight. The
1 MB write cap in `checkRequest` also means an unusually heavy resized
photo could be refused with a generic save error. No failure observed
today — a scale note, not a defect.

### F7 — INFORMATIONAL (state): live deploy state of PRs #31/#32 is unconfirmed

This audit covers the code at `main` `7cd5c13`. Whether the VPS has
pulled PR #32 and applied migration `0010` could not be verified from
the sandbox; `/api/health` returning `{"ok":true}` on the live host
remains the owner's confirmation signal.

## Areas reviewed and found sound

- **API surface**: every route is behind `secureRoute` with an explicit
  permission, except login (public, throttled) and `/api/health`
  (public, returns only `ok`/reason — database and schema names go to
  the server log only). No raw-fetch-without-status-check, no swallowed
  client errors (workflow audit enforces both mechanically).
- **Money**: server-side repricing (`pricing-core` shared with the
  client), overpayment and refund-tender caps enforced in the routes,
  advisory-lock idempotency on payments, tendered-vs-applied separation
  for change. All exercised by the battery, including rollback tests.
- **Permissions**: role defaults + sanitized per-user overrides
  (booleans for known keys only); owner accounts are structurally
  un-limitable; staff/permission/menu-removal owner rules check the
  **role**, so overrides cannot elevate; permission saves bump
  `sessionVersion` (revoking sessions) and are audit-logged. Menu
  deletion is archive-based, so order history and reports survive it.
- **RLS / multi-tenancy**: branch-scoped transactions, runtime role
  refuses BYPASSRLS at request time, cross-branch checks in the battery.
- **Auth**: scrypt hashing, login/PIN throttling persisted in the DB,
  signed expiring sessions, CSRF origin + JSON content-type gate (the
  415 behaviour is intentional and documented in `OrdersHistory`).
- **New client code (PR #29)**: scramble effects are confined to
  sidebar branding (never money, names or order numbers); the cart Undo
  is local-only and genuinely reversible; receipt "Sent to printer"
  means the print dialog finished, not printer telemetry; the
  TactileButton colour-loss bug found on the live till (PR #30) is
  fixed by placing colour on the face span and the trap is documented
  in the component.
- **Configuration & secrets**: no credentials in source; only
  `.env.production.example` is tracked; `.gitignore` blocks env files,
  databases and dumps; CSP + frame/nosniff/referrer/HSTS headers are
  set in `next.config.ts`; the only `dangerouslySetInnerHTML` is the
  static, allowlist-based display-size bootstrap in `layout.tsx`.
- **Hygiene**: no TODO/FIXME debt in `src`/`scripts`; migrations
  0000–0010 are sha-tracked and the schema guard covers every required
  column including `menu_items.is_archived`; the release packaging
  check passes.
