## Findings, most severe first

### N1 — CRITICAL (release blocker): Next.js 16.4.2 is vulnerable and now blocks both build and CI

The installed `next` 16.4.2 falls in the range of advisory
[GHSA-mfr8-8qww-v76h](https://github.com/advisories/GHSA-mfr8-8qww-v76h)
(16.3.0–16.4.4, information disclosure). Two consequences:

- `next build` stops with `SecurityFatalError`, so no new build can be produced or deployed.
- `npm audit --omit=dev` exits non-zero, so the *Security regression* workflow fails on every PR and every push to `main`.

**Recommendation:** raise `next` and `eslint-config-next` to `^16.4.6` (16.4.5 and later are fixed). Refresh the lockfile, then re-run the full battery: typecheck, lint, build and `test:security`. This is an in-range patch upgrade; it needs no `--force`.

### N2 — CRITICAL (data exposure): the legacy databases are retrievable from the public repository (F1, now confirmed)

`iwani1/claude-test` is still **public**. Its history still contains, as
fully retrievable blobs:

| File | Removed in | Size |
|---|---|---|
| `2026-10-12_restpos.db` | `ad6e134` | 2.9 MB |
| `2026-10-15_restpos.db` | `be3524e` | 2.9 MB |
| `11claude.zip` (original source drop) | `4cbbc90` | 0.7 MB |

Anyone who clones the repo can recover them with one `git show` on the parent commit. The last audit could not
confirm this from a shallow checkout; it is now confirmed. The file
contents were deliberately **not** opened during this audit.

**Recommendations, in order:**
1. Make the repository private now. This is the only step that stops new downloads.
2. Treat the data as exposed: rotate every credential the legacy DB held or shared (staff passwords and PINs reused in the new system, the `pos_owner` database login, any integration keys). Assess whether customer or staff personal data is affected.
3. Purge history: run `git filter-repo --invert-paths --path 2026-10-12_restpos.db --path 2026-10-15_restpos.db --path 11claude.zip`, force-push every branch and tag, delete or recreate stale branches and PR refs, and ask GitHub Support to remove cached views. Every existing clone, including the VPS checkout, must be re-cloned.
4. Have the VPS pull with a read-only **deploy key** instead of relying on public HTTPS. That need is what made the repo public in the first place.
5. Add a pre-commit or CI guard that rejects `*.db`, `*.sqlite`, `*.zip` and dump files.

### N3 — HIGH (fraud risk): till staff can remove or swap items on an open bill with no approval and no audit trail

`PATCH /api/orders/[id]/edit` lets anyone with `canAccessPos` replace the
whole item list of an unpaid or partially paid order. The carve-out was meant
for *adding* items to a reopened ticket, but it does not compare against the
existing lines, so a cashier can also **remove** or **downgrade** items. By
the recorded owner decision, the route writes **no audit entry**.

The theft pattern: ring up the full bill, let the kitchen cook it and collect cash from the guest. Then remove items, record payment for the smaller total and keep the difference. Only the kitchen docket (overwritten by the same edit) and the stock ledger would hint that anything happened.

**Recommendations:**
- For callers without `canEditOrders`, allow only additions: refuse when any existing line is missing or has a lower quantity, or require a manager PIN (same flow as refunds) to reduce or remove lines.
- Always write an audit row for line reductions and removals, recording who did it and a before/after diff. Revisit the "no audit on edit" decision at least for removals; the owner can still choose to hide it from the default log view.
- Report removed-after-kitchen items as a void line in Reports, as most POS systems do.

### N4 — HIGH (fraud risk): any till user can cancel an unpaid order; the audit row has no actor

`PATCH /api/orders/[id]` (gate `canAccessPos`) accepts `status: "cancelled"`
for any unpaid order without manager approval:

- It can optionally return stock (`returnStockOnCancel`), even after the food was prepared.
- The audit insert (`action: "order_updated"`) carries **no `userId`/`userName`**, so the log cannot say who voided the order.

This is the classic way to make a cash sale disappear: take cash for an order that was never paid in the system, then void it.

**Recommendations:**
- Require a manager PIN to cancel an order that has been sent to the kitchen.
- Always record the actor.
- Allow stock return only when the kitchen ticket was never started.
- Show voids per staff member in the shift close-out.

### N5 — HIGH (insider privilege escalation): a manager can discover the owner's PIN and switch into the owner account

PINs must be unique per branch (`users_branch_pin` index). When a PIN is already taken, `create_employee` and `update_pin` reply *"That PIN is already used by another staff member in this branch"*. This creates a PIN-discovery path:

- **Unthrottled and unaudited:** a manager (`canManageStaff`) can call `update_pin` on any cashier account and try every 4-digit PIN. Nothing limits the attempts, and nothing is logged, because the failed request rolls back. Within minutes they learn every PIN in use, including the owner's.
- **No barrier to the owner's account:** `POST /api/auth/switch-pin` then lets them become the owner with that PIN. The 10-per-15-minute throttle is no barrier when only a handful of PINs are in use.
- **What they gain:** owner-only powers, such as deleting orders, editing settled bills and changing settings and permissions.

**Recommendations (any one breaks the chain; do the first two):**
- Do not let quick PIN switch reach `super_admin` accounts. The owner signs in with a password, or with a PIN plus a second factor.
- Make the server generate PINs (random, unique, shown once) instead of reporting collisions. Alternatively, throttle and audit collision responses per actor.
- Raise the PIN minimum to 6 digits for manager and owner accounts.

### N6 — MEDIUM: refund approval and discounts ignore per-user permissions

The refund route accepts a manager PIN if `manager.role` is `manager` or
`super_admin`. It does **not** check that account's effective permissions, so a manager whose `canIssueRefunds` the owner revoked can still authorise refunds with their PIN. Discounts and complimentary orders on order creation are also gated by role (`create-order.ts:93`), not by a permission the owner can manage. This contradicts the per-user permission model introduced in PR #27.

**Recommendation:** check the approver with
`effectivePermissions(manager.role, manager.permissionOverrides).canIssueRefunds`.
Add a `canApproveDiscounts` permission (default: manager and owner) and use it in both `create-order.ts` and the edit route. Extend `audit:workflows` with a rule against role-literal checks outside `staff/route.ts`.

### N7 — MEDIUM: ten audit-log writes record no actor

These inserts omit `userId`/`userName`, so the activity log cannot say who did them:

- `order_updated` (including cancellations, see N4)
- `menu_item_created`, `menu_item_updated`, `menu_item_deleted`
- `ingredient_created`, `recipe_saved`, `stock_count_recorded`
- `purchase_order_created`, `goods_receipt_processed`, `supplier_created`

Price changes and stock counts are exactly the entries an investigation needs.

**Recommendation:** add one `audit(action, entity, details)` helper that takes the actor from `requestContext`. Make `audit_logs.user_id` `NOT NULL` for new rows, apart from system events. Add a workflow-audit rule that flags direct `insert(auditLogs)` calls.

### N8 — MEDIUM: menu photos will break the offline menu cache (F6, consequence found)

Each dish photo is stored as a data URL of up to 380 KB and returned with every `GET /api/menu`. The till caches that response in `localStorage`, which browsers cap at about 5 MB per origin. After roughly a dozen photos, `saveMenuToCache` fails; it only logs a console warning. The device then keeps whatever older menu it cached before. Offline, staff ring up stale prices and items, and the server re-prices the order at sync, so the guest is quoted one total and charged another.

**Recommendation:** store photos as files and send only their URLs in the menu payload. The app already serves `public/menu-images` and has a service worker that can cache images. At minimum, strip `imageUrl` data URLs before caching, and show a visible "offline menu out of date" warning when the cache write fails.

### N9 — LOW: viewing an order locks it

`GET /api/orders/[id]` reads the order with `SELECT … FOR UPDATE`. An accountant or cashier opening a receipt briefly blocks payments and edits on that order. Remove `.for("update")` from the read path.

### N10 — LOW: order status can move backwards; malformed IDs return 500

`PATCH /api/orders/[id]` accepts any of `confirmed/preparing/ready/served/cancelled` from any non-closed state, so a `completed` order can be set back to `preparing`. It also does not validate the ID, so a non-numeric ID becomes a 500. Add an allowed-transition table and the same `Number.isSafeInteger` check the other order routes use.

### N11 — LOW: request-boundary edge cases

- An `Origin: null` header (sent from sandboxed frames and some redirects) makes `new URL(origin)` throw, so the request returns a 500 instead of a 403. Wrap the parse.
- The 1 MB body cap trusts `Content-Length`; a chunked request without one is not limited. Enforce the limit at the reverse proxy (`client_max_body_size 1m` on nginx), or read the body with a byte limit.

### N12 — LOW (latent): an item edit without discount or tip fields wipes them

In the edit route, when a re-price omits `discountAmount` or `tipAmount`, they are treated as **0**, not as "unchanged". Today's clients always send both, so nothing breaks yet. A future caller (or N3's fix) could silently remove a manager-approved discount. Default to the order's existing values.

### N13 — LOW (availability): PIN throttles are shared across the branch

Ten wrong PINs from anyone in a branch lock **every** till in that branch out of quick switch, or out of refunds, for 15 minutes. One person mistyping can halt quick switches mid-service. Key the counters per device or per account, with a higher branch-wide ceiling as the backstop.

### N14 — INFORMATIONAL: development-tool advisories

`esbuild` (via `drizzle-kit`) and `minimatch` carry moderate advisories in development tooling only, so they are not in the production tree. Standing policy holds: no `npm audit fix --force`. Re-check after the N1 upgrade.

## Areas reviewed and found sound

- **Request boundary:** all 30 business route exports go through `secureRoute` with an explicit gate; login is the only `secureRoute` export marked public. `GET /api/health` is the one route outside `secureRoute`: it is intentionally public and returns only `ok` or a reason code. Sessions are re-validated against `session_version` and the live user row on every request, and the runtime role is refused if it can bypass RLS.
- **Tenant isolation:** FORCE RLS on all operational tables, keyed to a transaction-local branch setting, with composite foreign keys. Authentication lookup mode is read-only and switched off before handlers run.
- **Payments:** row lock, advisory-lock idempotency with request fingerprints, integer minor units, exact split totals, an overpayment cap, money posted to the operator's own shift, and an atomic ledger, balance, shift and audit update.
- **Refunds:** manager PIN required, cumulative and per-tender caps, linked drawer outflows, and stock restored from the original movements.
- **Passwords and sessions:** scrypt (N=32768), constant-time HMAC token comparison, HttpOnly/SameSite cookies, no PIN hashes sent to clients, and DB-backed login throttling that survives rollback.
- **Headers:** CSP with no external origins and no `unsafe-eval`, frame denial, `nosniff`, `no-referrer`, and HSTS in production.
- **Service worker:** never caches `/api/` and intercepts GET only.

## Maintainability notes (no defect)

- `PosTerminal.tsx` is 2,424 lines, and five other components are 760–985 lines. Splitting the till into cart, payment and order-loading modules would make N3/N4-style changes safer to review.
- Error handling is split between `throw new ApiError` (newer routes) and `try/catch` returning `{ error: err.message }` (older ones). `secureRoute` masks the 500 bodies, but the newer style is easier to audit. Migrate when touching those routes.
- `test:security` cannot run as root, because embedded PostgreSQL refuses it. Note this in `SECURITY.md`, or make the runner create its data directory with permissions the `postgres` user can use, so the suite runs in containers and CI images that use root.
